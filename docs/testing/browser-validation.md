# Executed browser validation

**PASS: a real Chromium browser executed the synthetic application through its UI and the actual three-process stack.** The machine-readable record is `browser-results.json`; the runner is `apps/unit-client/browser-check.mjs`. This is a local engineering test, not external assurance or a hosted CI result.

The test used separate browser contexts for Alice, Bob and the administrator, a fresh synthetic database, and the real web gateway, control authority and ciphertext relay. It exercised mandatory MFA, encrypted provisioning imports, device binding, endpoint encrypted text exchange, cryptographic release verification, recipient decryption and acknowledgement. Hostile HTML-shaped content stayed text and did not execute.

The administrator denied the Unit A → Unit B policy while Alice queued work under simulated disconnection. Reconnection held the object. A later explicit allow permitted controlled release. Browser storage was checked for absence of the plaintext message, private signing key, password and TOTP seed. A separate **actual browser network-offline toggle followed by page reload** restored the cached public shell and encrypted vault, allowed bounded local queuing under the cached grant, and required fresh MFA before reconnecting to the server. No uncaught browser errors were observed.

A real failure was found and fixed: HTML labels wrapped select controls, causing their accessible names to include option text. The DOM helper now creates unique input IDs and separate labels. The full browser sequence passed after this change; the policy-form path is its regression coverage. Nine focused Node regressions cover exact challenge validation, release-receipt scope, stale snapshots, cooperative lock serialization, unsupported locking, failure to write durable browser storage, and exact public-only trust pin/metadata handling.

A subsequent security review found and fixed three client issues: signing server challenges without locally checking their complete scope; accepting a correctly signed non-release record on digest checks alone; and treating a localStorage compare/write as atomic across tabs. The client now validates the exact challenge schema and locally intended fields, requires a release receipt scoped to the recipient/device/object/action, and holds an exclusive Web Lock around each encrypted-vault comparison and write. Unsupported locking fails closed.

The complete browser suite was rerun after these fixes. It also generated a fresh Bravo device in the browser, rejected a modified challenge before sending any proof, rejected encryption-key substitution in the enrollment body, prevented binding before administrator approval, and successfully bound the approved device. Two actual tabs competed for the same vault key; exactly one committed and the stale writer was rejected. This establishes cooperative locking among current client tabs, not protection against malicious same-origin code that ignores the lock.

The final run added the existing file-exchange path: a synthetic multilingual UTF-8 `.txt` file passed through the browser file input, endpoint encryption, authority release, recipient decryption and a real attachment download. The downloaded bytes and suggested filename matched exactly. An unsafe `..` filename was rejected before any object submission. An untrusted `text/html` MIME hint was replaced by `application/octet-stream` for download; this is content-type coercion, not malware inspection. All earlier browser scenarios passed in the same final run.

The normal Playwright Chromium downloader returned an invalid/truncated archive in this environment. A scratch-only npm-packaged Chromium binary was used instead. Its archive was extracted without changing ownership, and GPU-dependent rendering was disabled for this container. Browser web-security controls were **not disabled**. Services and the browser were spawned within one execution context because independent tool executions had isolated loopback namespaces. Exact versions and findings are recorded in the JSON file.

The 1440-pixel recipient and authority screenshots were visually inspected; no material clipping or overlap was found. Generated screenshots are in `artifacts/browser/recipient.png` and `artifacts/browser/authority.png`. Those paths are generated test artifacts, not proof that another environment has passed.

Reproduce against a fresh synthetic deployment using the command in `apps/unit-client/README.md`, with a functioning Chromium installation. The runner changes the synthetic policy and consumes current TOTP codes. The hosted GitHub Actions browser job remains **pending execution** until an actual run reports its result.

This run does not establish all browser engines, hardware-backed keys, endpoint-compromise resistance, or production readiness. API, cryptographic, race, recovery and independent-evidence results belong to their separate test records.

A later hosted scan classified the public authority key’s clear-text trust-pin persistence as sensitive storage. The client was hardened to store only a SHA-256 fingerprint as the pin, reject private/extra fields in authority public keys, validate their curve point through WebCrypto and cache only allowlisted public metadata. Legacy public-key pins migrate to digests. Two trust-storage regressions passed, and the complete real-browser suite was rerun successfully after this change; the [separate post-hardening record](browser-results-trust-pin.json) preserves that execution. The hosted rescan remains a separate result; no scanner suppression was added.
