# ADR-011: keep wrap v2 for the laboratory; HPKE base mode is the planned wrap v3

Status: accepted for laboratory use, 2026-10-08.

## Context

Wrap v2 (ADR-010) is a project-defined KEM → HKDF-SHA256 → AES-256-GCM key schedule. The
standards-track alternative is HPKE base mode with post-quantum KEMs (`draft-ietf-hpke-pq`:
ML-KEM `0x0041`/`0x0042`, MLKEM768-X25519 = X-Wing `0x647a`). Evaluation and sources:
`research/cryptographic-standards/HPKE_PQ_EVALUATION.md`. Specification of the current composition:
`research/cryptographic-standards/V3_COMPOSITION.md`.

## Decision

- Keep wrap v2 for laboratory objects. Do not add an HPKE dependency now: the npm candidates
  predate the current editor's copy, bring a second unaudited ML-KEM implementation beside
  OpenSSL, and Node 24 has no HPKE API.
- Reserve wrap `schemaVersion: 3` for HPKE base mode, single-shot, KDF HKDF-SHA256 `0x0001`,
  AEAD AES-256-GCM `0x0002`, application `info` = canonical `{providerId, suiteId,
recipientKeyId, contextDigest}`, `aad` = the wrap v2 AAD bytes. Sender authentication stays with
  the ML-DSA-65 and P-256 signatures (these KEMs have no Auth mode).
- Adoption gates: published HPKE-PQ codepoints match the record; the implementation passes the
  `hpke-pq` vectors for each KEM ID used and vectors for the exact suite above generated by the
  reference implementation; independent review accepts the mapping.
- Wrap v2 stays pinned by `tests/crypto-agility/wrap-derivation.test.mjs`. Any change to its bytes
  requires a new wrap schema version; v2 objects remain readable only under explicit legacy policy.

## Consequences

No wire change in this ADR. The composition remains laboratory-only and unreviewed; production
crypto policy still forbids every laboratory suite.
