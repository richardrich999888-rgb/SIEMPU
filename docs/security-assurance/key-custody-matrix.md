# Authentication, device trust and key custody

Reviewed 8 October 2026. This document defines evidence requirements for the laboratory programme. It does not declare hardware deployed, attestation achieved or cryptography approved. See [public source records](../../research/defence-comparison/sources.json) and [current execution status](../../research/trl56/20-q-agile-execution.md).

## Security-property matrix

| ------------------------------------------ | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Password/TOTP plus software key possession | Account factors and possession of an enrolled signing key                                                 | Genuine hardware, nonexportability, measured boot or absence of malware                                    | Enrollment/session/device binding; replay/revocation/recovery tests. | WebAuthn authentication [D09]              | RP-scoped public-key authentication and user verification when required and checked; optional attestation | Hardware custody of the separate E2EE key; all credentials being device-bound; endpoint software integrity | Origin/RP ID, challenge, signature, UP/UV, backup-eligibility and allowed-attestation policy; replacement and revocation tests            |

| TPM-bound key [D10–D11]                    | Protected key operations subject to authorization and object attributes                                   | Whole-device health from proof of possession alone; support for every desired suite                        | Genuine-device/provisioning evidence, key creation provenance and attribute checks; unauthorized-use and duplication tests                |

| SoftHSM/swtpm [D14–D15]                    | Repeatable software interface, state and failure-path experiments                                         | Physical tamper resistance, production attestation or hardware qualification                               | Label `SOFTWARE_EMULATED`; record exact versions and repeat required tests on the actual target                                           |

W3C WebAuthn Level 3, dated 25 August 2026, explicitly supports backup-eligible multi-device credentials. A successful WebAuthn ceremony is therefore not a nonexportability certificate. Policy must identify whether synchronized credentials are permitted; that decision must not silently change recipient-key custody.

TCG TPM architecture v185 describes `fixedParent=1` and `fixedTPM=1` as a nonduplicable object created on a specific TPM. These attributes and a software signature are insufficient to establish genuine hardware provenance without the applicable provisioning and attestation evidence. TCG provisioning separates identity, protected storage and measurement attestation. RFC 9683 is an Informational workflow; it defers continuous in-memory runtime attestation.

OASIS approved PKCS#11 3.2 on 3 June 2026. Record the actual implementation's negotiated interface and mechanisms; do not assert 3.2 support merely because the standard exists. Existing sensitivity/extractability semantics can be checked against the cited 3.1 standard. A token's mechanism list, hardware assurance and sponsor approval are separate records.

## Provider and lifecycle requirements

For each enrolled key, retain a public record of purpose, suite, provider/version, stable key identifier, custody backend, export policy, attestation status, activation/retirement state and evidence reference. Do not log private keys, PINs, recovery secrets or plaintext. An unverified client assertion of hardware status must never raise authorization.

The provider interface should return opaque handles for private keys. Signing, decapsulation or unwrapping occurs through the selected provider. A missing token, unsupported mechanism, timeout or failed attestation must return an explicit error; it must not silently import private material into software or select a weaker suite. Host plaintext after authorized decryption is a separate endpoint risk even when long-term keys remain inside hardware.

Provision replacement devices through an authenticated recovery process; revoke the old device and key, retain public verification material needed for historic evidence, and record policy changes. Define whether old content remains decryptable and by whom. Rewrapping cannot make ciphertext already captured under a vulnerable historical key-establishment scheme retroactively quantum-resistant.

## Minimum custody experiment

1. Record runtime, module, hardware/firmware or emulator identity, selected mechanism and synthetic workload.
2. Generate the key through the provider and retain only its public key and opaque handle in application state.
3. Prove required operations and independent verification; attempt disallowed key export and wrapping.
4. Remove/lock the provider and retry: require an explicit failure with no alternate key or suite.
5. Restart the application and provider; prove durable handle resolution, revoked-key denial and audited recovery.
6. Repeat on the qualified target; compare semantic results and performance. Software-only passes leave HQ gates open.
