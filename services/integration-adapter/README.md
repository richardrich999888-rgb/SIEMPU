# Synthetic ciphertext submission adapter

`createIntegrationAdapter` exposes `GET /integration/versions` and `POST /integration/v1/submissions` over authenticated TLS only. The independent emulator in `deployment/testbed/legacy-emulator.mjs` signs the public context using Node crypto and its own canonical encoder. No IAF protocol, network endpoint or integration approval is implied.

The exact context includes protocol `SIEPMU-SYNTHETIC-INGRESS`, version `1`, source/key identifiers, nonce, idempotency identifier, issuance/expiry timestamps, and the encrypted SIEPMU submission plus its one-use device proof. The source's P-256 SHA-256 signature binds all context fields. Its signing key identifier is SHA-256 of canonical public JWK. The adapter's fixed source registry binds that key to the mTLS certificate and authorized sender device, destination units and missions. Unknown fields, versions, sources, invalid signatures and stale contexts fail closed.

The endpoint encrypts and signs the object before the adapter receives it. The adapter needs only its TLS private identity, registered public source keys and a current endpoint-provided bearer session; it has no endpoint private encryption/signing keys. It forwards ciphertext submissions only to the configured public control API. There is no key release, plaintext, administrator, arbitrary URL or generic proxy route.

SQLite WAL/FULL stores used nonces, a logical encrypted-object digest and completed public submission responses. Bearer tokens, device proofs and complete submitted ciphertext are not persisted there. Nonces are retained until their signed context expires. Retried requests need a fresh nonce; the same logical idempotency key returns the original submission receipt, while altered encrypted content produces a conflict. A cached receipt is historical evidence of submission, not a new authorization or recipient key issuance. Every new submission still traverses live control authorization. Current recipient authorization is separately rechecked by the release engine.

A crash or transport failure after reserving an idempotency key leaves `PENDING`; subsequent requests return `RECOVERY_REQUIRED`. The adapter deliberately does not guess whether the authority committed. An authorized operator must inspect the public object's status/evidence; a fresh idempotency key and fresh endpoint operation proof may resubmit the identical object, relying on the control object's own idempotence. Do not edit adapter database rows to force success. This conservative quarantine sacrifices automatic recovery for unambiguous admission. Storage exhaustion is explicit `ADAPTER_CAPACITY`, not deletion of replay history.

Local audit rows correlate source, idempotency ID and outcome but are not independently signed audit evidence. Successful forwarding preserves the authority's signed submission receipt. Independent custody of adapter logs, live source registry rotation, authorization lifecycle procedures and external interface specifications remain qualification work.

Acceptance tests prove independently signed admission, strict rejection, scoped authorization, persistent replay denial across restart, idempotency without duplicate forwarding, exact-byte decryption through the public control API, live revoked-device denial and pending-state quarantine. No network or crypto dependency was added; Node core modules retain the repository's existing Node license/runtime baseline.
